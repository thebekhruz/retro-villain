# Retro Milliy: мобильный модуль директора — iiko, меню и продажи

Дата: 18 сентября 2026 г. Статус: согласованный дизайн для ревью перед планированием.

## Цель и границы v1

Модуль 03 — mobile-first экран директора ресторана. Он отвечает на два вопроса: что происходит сегодня и какие решения по меню нужно принять по данным последних десяти полных дней iiko. Главный экран начинает действие «Сформировать отчёт», а не с длинной таблицы.

В v1 входят: быстрый обзор выручки, честный статус посещаемости, ручной запуск анализа меню, AI-вывод по десяти главным проблемам, сравнение официантов, история неизменяемых отчётов и скачивание PDF. Модуль работает только с прочитанными данными iiko; он не меняет чеки, меню, цены или сотрудников.

Не входят: интеграция Hikvision, контроль опасных операций (изменение счёта, удаление позиции, отмена, скидка, возврат), кадровые решения, автоматический запуск по расписанию, Excel-выгрузка и удаление истории. Эти пункты не маскируются демоданными: на экране они имеют статус «Интеграция ожидается» или «Будет добавлено».

## Значения и разрезы

День — календарный день `Asia/Tashkent`; отчётный период — десять последних завершённых дней, не включая незавершённый текущий день. При запуске 18 сентября период равен 8–17 сентября включительно. Сформированный отчёт сохраняет этот период и больше не меняется.

На быстром обзоре показываются три самостоятельных показателя:

| Показатель | Правило | Входит в общий итог касс |
| --- | --- | --- |
| Retro | Продажи с `Kassa-FiscalBox1`, кроме отделения `Бехруз (Свадьба)` | Да |
| Oxbridge | Продажи с `GL-Kassa-Oksbrich` | Да |
| Yandex | Продажи с типом оплаты `Яндекс Еда` (вариант iiko `Яндех Еда` нормализуется) | Нет, это канал, пересекающийся с Retro/Oxbridge |

Общий итог касс = Retro + Oxbridge. Yandex показан как отдельный канал и никогда не прибавляется повторно к этому итогу. Продажи отделения `Бехруз (Свадьба)` в модуль директора v1 не входят, как и в кассовый отчёт Retro.

## Экран директора

`/director` — третий модуль в существующей навигации. Он использует существующий FastAPI + статический HTML/CSS/JS стек и остаётся удобным с ширины 320 px.

1. Верхний блок «Меню: новый анализ» показывает период, дату последнего успешного отчёта и кнопку «Сформировать отчёт».
2. Под ним «Сегодня · быстрый обзор»: Retro, Oxbridge, Yandex и общий итог касс. У каждой суммы есть время обновления и источник iiko.
3. Блок «Команда»: «Пришли сегодня» и «Опоздали» со статусом «Интеграция ожидается». Значения не подставляются как ноль или как демо.
4. Блок опасных операций сообщает, что контроль будет добавлен после отдельного согласования; он не выдаёт пустой список за отсутствие рисков.
5. История показывает отчёты по дате формирования и периоду. Открытие отчёта ведёт на `/director/reports/{id}`, PDF доступен отдельной кнопкой.

Страница отчёта содержит общую сводку, внутренние разрезы Retro/Oxbridge/Yandex, топ-10 проблем меню, раздел официантов, методологию и кнопку PDF. Все текстовые значения экранируются; iiko и Claude не могут добавить HTML или исполняемый код в браузер либо PDF.

## Получение и нормализация iiko

Кнопка создаёт единственный запуск для данного периода. Пока он выполняется, повторная кнопка заблокирована, а интерфейс последовательно показывает «Получаем iiko», «Проверяем данные», «Анализируем», «Собираем PDF». Новый запуск не заменяет старый отчёт.

Расширение `IikoClient` получает для каждого из десяти дней агрегированные строки продаж с обязательными полями: дата, касса, отделение, тип оплаты, позиция, категория позиции, количество, выручка после скидок, себестоимость, официант и идентификатор заказа. Идентификатор заказа применяется только для проверки уникальности и не передаётся Claude. Запросы сохраняют существующие защиты: только настроенный сервер Retro Milliy, `SALES`, исключение удалённых заказов/позиций, void и non-business payments.

Сервер допускает в отчёт только позиции, чья категория из iiko относится к основному меню, десертам или напиткам. Фильтрация происходит до всех бизнес-расчётов. Категории определяет iiko, не браузер и не Claude. Для каждой строки сервер дополнительно определяет направление Retro/Oxbridge и канал Yandex; канал допускается пересекающимся с направлением.

Генерация отклоняется, если iiko не вернул полный период, если не хватает любого обязательного поля, если сумма по агрегированным позициям не совпадает с суммой направлений с точностью до 1 UZS, либо если обнаружена неизвестная касса/категория, которую нельзя классифицировать. Ошибка называет отсутствующее поле или непроверенный справочник; данные не подменяются нулём.

## Расчёты и Claude

До обращения к Claude сервер считает по каждой позиции и по каждому официанту:

- количество проданных единиц;
- выручку после скидок;
- себестоимость;
- валовую прибыль = выручка − себестоимость;
- маржинальность = валовая прибыль / выручка, только при положительной выручке;
- долю позиции и сотрудника в соответствующем разрезе.

Claude получает только этот нормализованный агрегат, период и определение метрик. Ему не передаются пароль iiko, секрет Claude, полные чеки, идентификаторы заказов и персональные данные гостей. Ключ Claude хранится только в `build/.env`; в браузер он не передаётся и не попадает в PDF, логи или git.

Claude обязан вернуть JSON, который проходит серверную валидацию: короткое резюме, ровно до десяти неповторяющихся проблем, для каждой — позиция или группа, направление, наблюдаемые метрики, объяснение, приоритет `high|medium|low` и действие `remove|replace|promote|review`. Модель предлагает решение, но не выдаёт команду: PDF и экран явно помечают рекомендации как материал для решения директора. Некорректный, неполный или невалидируемый ответ не сохраняется как отчёт.

## Официанты

Раздел «Официанты» использует тот же снимок десяти дней. Для каждого официанта показываются выручка, количество позиций, средняя выручка на заказ, валовая прибыль проданных позиций и сравнение со средним по команде. Разрез отображается как оценка продаж за период, а не как кадровое решение. Отсутствие официанта в iiko блокирует отчёт, потому что нельзя заменить неизвестные данные произвольным «не указан».

## Хранение, PDF и API

Новая отдельная SQLite-база `build/director.sqlite3` хранит неизменяемые отчёты. Каждый отчёт содержит UUID, время запуска и завершения, период, нормализованный снимок iiko, проверенные метрики, JSON Claude, SHA-256 PDF и сам PDF в BLOB. Исходные, неочищенные HTTP-ответы iiko не сохраняются. База резервируется вместе с `cashier.sqlite3` и `accountant-demo.sqlite3`; в git она не попадает.

Маршруты v1:

- `GET /director` — мобильный экран;
- `GET /api/director/today` — быстрый обзор без демоданных;
- `POST /api/director/reports` — создаёт один отчёт за фиксированные последние десять завершённых дней;
- `GET /api/director/reports` — история;
- `GET /api/director/reports/{id}` — сохранённый отчёт;
- `GET /api/director/reports/{id}/pdf` — `application/pdf` с безопасным именем файла.

PDF — самостоятельный оформленный документ: период, время формирования, источник iiko, общая сводка, три разреза, топ-10, официанты, методология и предупреждение о рекомендациях Claude. Скачать можно только уже успешно сохранённый PDF; файл никогда не строится заново из изменившихся данных.

## Доступ, ошибки и проверка

Модуль наследует существующие ограничения дашборда: локальный доступ по умолчанию, Basic Auth при доступе из сети, `Cache-Control: no-store`, CSP и запрет внешнего фрейминга. Внешняя публикация отчётов без включённой аутентификации запрещена.

Проверки перед приёмкой:

- 10 завершённых дней выбираются корректно в `Asia/Tashkent`; текущий день не попадает в период.
- Retro, Oxbridge и Yandex определяются по приведённым правилам; общий итог не включает Yandex повторно и не включает банкет Бехруз.
- Не-меню, не-десерт и не-напиток не передаются Claude; неизвестная категория, касса или отсутствующее обязательное поле останавливают запуск с понятной ошибкой.
- Себестоимость, валовая прибыль, маржинальность, направление и Yandex-канал правильно считаются на детерминированной фикстуре, включая нулевую выручку и скидки.
- В Claude уходит только разрешённый агрегат; невалидный JSON, таймаут и отказ API не создают частичный отчёт.
- Повторные нажатия одного запуска не создают дублей. Успешно сохранённый снимок и PDF не изменяются после новой загрузки iiko.
- PDF совпадает с сохранённым отчётом, безопасно скачивается и корректно отображается на телефоне.
- На ширине 320 px доступны кнопка запуска, быстрый обзор, история и PDF; Hikvision и опасные операции имеют явные статусы ожидания, а не нули.
