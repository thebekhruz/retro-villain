# Аудит производительности retro-villain

Основная подтверждённая проблема — повторное построение отчётов iiko внутри запроса страницы и общая очередь между модулями. Дополнительно найдены синхронные операции SQLite внутри асинхронных обработчиков, отмена чужого кассового запроса и ожидание медленного источника перед отображением уже готовых данных.

Проверены касса, бухгалтерия, директор, учредитель, их API, интеграции iiko/Hikvision/бронирований/Claude, SQLite, загрузка ресурсов и настройки запуска. Код исследован на указанном коммите `origin/main`, в отдельной ветке `codex/retro-performance-audit`. Незакоммиченные изменения других рабочих копий не использовались.

Production измерен через Chrome Network на `https://dashboard.retro-milliy.uz` обычными открытиями страниц и одним обновлением директора. Нагрузочный тест production не проводился. SHA реально запущенного backend через deployment API не проверялся. Время ниже — отдельные замеры, не p50/p95. Производственные данные, credentials и cookie в артефакты не сохранены.

## Исправление T-367

Аудит ниже описывает состояние до исправлений. Реализация перенесена на `a5b6d9f` после T-366 и сохраняет разделение продаж, счёта шефа, дегустаций и прочих расходов без выручки.

- Директор: четыре параллельных OLAP за период вместо 22; одна авторизация и минимум девять HTTP-запросов вместо 45. Касса выполняет независимые выгрузки параллельно.
- Общий ограниченный кэш объединяет одинаковые запросы UI, PDF и чат-инструментов. Очередь входит в дедлайн; отключившийся читатель не отменяет работу другого; последний читатель освобождает ресурсы. Ошибка параллельной операции останавливает её оставшиеся запросы.
- Клиент iiko переиспользует соединения и токен; истёкший токен обновляется один раз. Сырые OLAP ограничены 16 записями и 12 MB сериализованных данных, готовые результаты — 64 записями, очередь — 128 уникальными расчётами.
- SQLite и PDF вынесены из event loop; Hikvision сохраняет события пакетом; схема создаётся при запуске, используется WAL. Зарплатные выплаты агрегируются за два SELECT с точной арифметикой Decimal. Страница сотрудников использует отдельный `/api/accountant/staff`.
- Блоки учредителя отображаются независимо; устаревшие ответы игнорируются. Config загружается один раз на страницу; JS/CSS ревалидируются через ETag/304. Конфиденциальные API сохраняют `no-store`.
- Добавлены безопасные тайминги очереди/расчёта, cache hit/miss и число fetch-попыток без содержимого отчётов.

## 1. P1 — 22 OLAP-расчёта при каждом открытии директора, без повторного использования результата

Источники: `retro/integrations/iiko.py:324`, `:340`, `:356`; `retro/modules/director/routes.py:56`; `retro/modules/director/service.py:12`; `retro/static/director.js:380`.

`load_director_report()` обходит десять дней последовательно. На каждый день запускаются две выгрузки параллельно: продажи по способам оплаты и себестоимость без разделения по оплатам. После десяти дней запускаются ещё две выгрузки оплат за период. Получается 22 OLAP-задачи, а не один запрос отчёта.

Каждая OLAP-задача требует `init` и минимум один `fetch`. Offline-проба настоящего адаптера через `MockTransport` насчитала **45 HTTP-запросов на открытие**: 1 авторизация + 22 init + 22 fetch. При неготовом отчёте fetch повторяется. Два одинаковых последовательных открытия: 2 авторизации, 44 init, 44 fetch — кэша нет.

Кнопка «Сформировать отчёт» повторно получает весь snapshot из iiko. Проверка сохранённого отчёта и повторное использование анализа Claude происходят только после этой загрузки. Инструмент директорского чата также вызывает полный расчёт. Учредитель при смене детализации или направлений повторно загружает исходный период, хотя эти параметры применяются к уже полученным строкам при агрегировании. Касса заново делает три OLAP-расчёта и запрос смен; её `SnapshotCache` в GET `/day` не читается.

Исправление: хранить снимки/дневные данные с временем актуальности; объединять одинаковые выполняющиеся запросы; повторно использовать один snapshot для страницы, PDF и чата. Для директора проверить выгрузку диапазона с `OpenDate.Typed` вместо десяти последовательных дневных итераций, либо обновлять только изменившиеся дни. TTL и принудительное обновление должны учитывать поздние исправления iiko.

Две выборки с `PayTypes` и без него нужны для правильной себестоимости смешанных оплат. Удалять эту сверку ради скорости нельзя: оптимизация должна сохранять финансовые итоги.

## 2. P1 — общая очередь iiko задерживает другие модули; время ожидания не входит в таймаут

Источники: `retro/app.py:118`; `retro/modules/founder/routes.py:67`; `retro/modules/director/routes.py:58`; `retro/modules/cashier/routes.py:122`; `retro/modules/accountant/routes.py:56`; `retro/modules/founder/tools.py:217`.

Один `app.state.iiko_lock` удерживается на весь расчёт. Директор, учредитель, касса и инструменты чата последовательно ждут друг друга. Бухгалтерия также подключается к этой очереди при выключенном ручном режиме сдачи кассы; на production сейчас `manual_handover=true`, поэтому этот конкретный путь там не активен.

В большинстве обработчиков конструкция выглядит как `async with lock: await wait_for(load(), timeout=...)`. Таймер начинается **после** получения блокировки. Локальная проба со сжатым таймаутом 50 мс и очередью 200 мс вернула успех через **210,9 мс**. Сам `/api/director/today` не имеет общего таймаута: `httpx timeout=25` ограничивает отдельные сетевые операции, а не весь набор отчётов и очередь.

На production выполнен обычный сценарий: открыть директора и спустя около восьми секунд перейти к учредителю. Учредитель ответил за 28,138 с вместо предыдущих 10,612 с. Рост согласуется с ожиданием оставшегося директорского расчёта; точное разложение по серверным этапам не установлено без трассировки backend. Уход со страницы не реализует отмену серверной работы в этих обработчиках.

Отдельная несогласованность: `POST /api/director/reports` использует `director_lock`, но `DirectorService.generate()` напрямую вызывает iiko, обходя `iiko_lock`. Поэтому блокировка одновременно создаёт очередь для страниц и не является общим ограничителем всей нагрузки на источник.

Исправление: общий координатор загрузок с ключами типа отчёта/периода, объединением одинаковых запросов и ограничением количества обращений к iiko. Дедлайн должен включать очередь. Устаревшие запросы интерфейса нужно отменять/отсоединять с учётом других потребителей результата. Кнопка обновления директора сейчас тоже не блокируется и не заменяет предыдущий запрос, поэтому повторные клики увеличивают очередь.

## 3. P1 — SQLite блокирует цикл обработки асинхронных задач

Источники: `retro/modules/accountant/routes.py:87`, `:102`; `retro/integrations/hikvision_poller.py:55`, `:85`; `retro/modules/accountant/hikvision.py:64`, `:96`; `retro/modules/director/service.py:20`.

Асинхронный бухгалтерский обработчик напрямую выполняет синхронные запросы `sqlite3`. Фоновый Hikvision poller делает то же самое; на каждое событие отдельно открывает соединение, проверяет схему и выполняет транзакцию. Запись в базу может ждать блокировку до 10 секунд. В асинхронной функции это время занимает поток event loop и задерживает другие запросы того же процесса. PDF тоже строится синхронно внутри `async generate()`, но его вклад отдельно не измерялся.

Локальное воспроизведение использует настоящий `HikvisionPoller.run_once()`, настоящую временную SQLite и конкурирующую транзакцию на 400 мс. Интервал между тиками независимой асинхронной задачи вырос до **473,1 мс** вместо примерно 10 мс. Это доказательство механизма, не измерение частоты production-зависаний.

Исправление: целые синхронные операции с SQLite вынести в ограниченный thread pool, создавать и закрывать соединения внутри этих операций; события Hikvision записывать пакетно в одной транзакции. Миграции схемы перенести из каждого `_open()` в инициализацию. WAL и индексы оценить отдельно. Правило об исполнении синхронных utility-функций описано в [FastAPI](https://fastapi.tiangolo.com/async/#other-utility-functions), перенос блокирующего I/O — в [документации Python](https://docs.python.org/3/library/asyncio-task.html#asyncio.to_thread).

## 4. P1 — один пользователь отменяет кассовый отчёт другого

Источники: `retro/app.py:119`; `retro/modules/cashier/service.py:33`, `:40`; `retro/modules/cashier/routes.py:125`; `retro/modules/accountant/routes.py:59`; `retro/modules/founder/tools.py:264`.

`LatestReportRunner` существует один на приложение. Любой новый вызов отменяет предыдущую задачу независимо от пользователя, даты и потребителя. Этим runner пользуются касса, автоматический расчёт сдачи бухгалтерии и кассовый инструмент чата учредителя.

Offline-проба двух разных пользователей на двух датах через настоящий `day_report()` дала **409 первому и 200 второму**. Это ошибка координации: вместо ускорения создаёт оборванные загрузки и необходимость повторять запрос.

Исправление: одинаковые расчёты объединять по ключу периода; замену запроса ограничить владельцем/экземпляром интерфейса. Отмена одного подписчика не должна обрывать общий расчёт, нужный другому.

## 5. P2 — готовые бронирования скрыты, пока не завершится медленная аналитика

Источники: `retro/static/founder.js:114`, `:115`; `retro/static/founder.css:207`.

`await Promise.allSettled([analytics, bookings])` выполняется до любого `render`. Ошибки источников разделены, но отображение результатов связано общей точкой ожидания. На production бронирования ответили за 0,230 с, аналитика — за 28,138 с. Код не отображает готовые бронирования до завершения аналитики; общий класс загрузки делает все панели полупрозрачными.

JS-проба выполняет **реальную функцию `load()` из файла**, подменяя только окружение и ответы: бронирования готовы на 21-й мс, отображены на 202-й мс вместе с аналитикой.

Исправление: независимо отображать и снимать состояние загрузки у каждого блока, сохраняя общий request-id для защиты от устаревших ответов. Если оставлять предыдущие данные во время обновления, явно показывать их прежний период и актуальность.

## 6. P2 — бухгалтерский расчёт растёт как N запросов с полным сканированием выплат

Источники: `retro/modules/accountant/ledger.py:393`, `:399`, `:401`, `:678`; `retro/static/employees.js:348`.

`FinanceStore.accruals()` выбирает все начисления до выбранного дня, включая полностью оплаченные, затем делает отдельный `SELECT` выплат для каждого начисления. Индекса по `(accrual_id, paid_day)` нет. `EXPLAIN QUERY PLAN` показал `SCAN accountant_salary_payments`.

| Синтетические начисления / выплаты | SELECT | Время `accruals()` |
|---|---:|---:|
| 1 000 / 1 000 | 1 001 | 0,038 с |
| 5 000 / 5 000 | 5 001 | 0,587 с |
| 10 000 / 10 000 | 10 001 | 2,119 с |

Это локальная модель роста, не объёмы production. В production-ответе бухгалтерии за 22 сентября **0 начислений**, 35 сотрудников, ручной приход; ответ 0,191 с. Поэтому эту ошибку нельзя объявлять причиной текущих 27-секундных загрузок директора.

Страница сотрудников также использует весь `/api/accountant/day`, получая вместе со списком финансовую сводку и историю расчётов.

Исправление: агрегировать выплаты одним запросом с JOIN/GROUP BY, добавить индекс, ограничить/разделить историю и текущие долги. Для сотрудников дать отдельный лёгкий read endpoint. При оптимизации сумм сохранить точную денежную арифметику; не заменять текущие Decimal расчёты без проверки округления SQLite.

## 7. P2 — браузеру запрещено кэшировать все CSS и JS

Источник: `retro/app.py:187`.

Middleware безусловно ставит `Cache-Control: no-store`, включая `/static/`. На production это подтверждено для всех 14 CSS/JS ресурсов, загружаемых панелью учредителя; ответы имеют 200 и `gzip`. При обычных переходах повторно передаются неизменившиеся ресурсы. Это дополнительная задержка навигации, но она не объясняет 26,8 с ожидания API.

Исправление: версионированные статические ресурсы с подходящим браузерным кэшем; для конфиденциальных API сохранить запрет HTTP-кэширования. Backend-кэш отчётов из пункта 1 — отдельный механизм, с контролем доступа и актуальности.

## Дополнительные усилители задержек

- Каждый вызов `IikoClient.load*` создаёт новый `httpx.AsyncClient` и заново авторизуется. Соединения используются внутри одного вызова, но не между открытиями страниц. После основных исправлений стоит добавить управляемое переиспользование клиента/токена; [HTTPX рекомендует избегать создания клиентов в горячем цикле](https://www.python-httpx.org/async/#opening-and-closing-clients). Отдельная стоимость авторизации на production не измерялась.
- `load_sales_details()` получает полный OLAP-ответ, затем применяет `limit <= 200` при формировании результата. Этот limit ограничивает ответ чат-инструмента, но не работу iiko, размер входного JSON или обход строк.
- Инструменты Claude выполняются последовательно, ответ чата показывается после полного завершения; директорский инструмент каждый раз строит десятидневный отчёт. Живые платные вызовы Claude в аудите не запускались.
- `BookingAnalyticsClient.load()` последовательно запрашивает submitted/cancelled. В текущих замерах весь API бронирований быстрый, это не приоритетная причина.
- `nav.js` и скрипт страницы отдельно загружают `/api/config`; на production видно по два запроса. Бухгалтерия также последовательно ждёт config → catalog → day. Это небольшие дополнительные сетевые задержки.
- Логи не содержат времени ожидания очереди, количества fetch и длительности успешных стадий. `duration_ms` предусмотрен в logging helper, но исследованные вызовы не передают измерения. Добавить тайминги без payload, credentials и cookie.

## Порядок исправления

1. Повторное использование snapshot и объединение одинаковых iiko-загрузок; дедлайн на очередь вместе с расчётом; исправление отмены чужих запросов.
2. Сокращение последовательных OLAP-этапов директора с сохранением сверки смешанных оплат; повторное использование snapshot для страницы, PDF и чата.
3. Перенос блокирующего SQLite I/O из event loop, пакетная запись Hikvision, измерение event-loop lag.
4. Независимое отображение блоков учредителя и управление повторными обновлениями директора.
5. Индексы/агрегация бухгалтерии, отдельный API сотрудников, кэш статических файлов.

Простое увеличение количества workers не заменяет эти исправления: сессии, snapshot cache и блокировки находятся в памяти процесса, а poller стартует в lifespan каждого экземпляра. Перед масштабированием нужно согласовать хранение сессий/кэша и единственного фонового сборщика. Реальные CPU/RAM, регион, replica count и переопределения команды Railway в этом аудите не проверены; нехватка ресурсов не доказана.

## Воспроизведение

Из корня этой рабочей копии:

```sh
PYTHONPATH=. python scripts/performance_probe.py
node scripts/performance_frontend_probe.mjs
```

Python-проба использует MockTransport, синтетических пользователей и временные SQLite внутри `build/`, удаляемые по завершении. JS-проба исполняет извлечённый `load()` без браузера и сети. Исходные JSON сохранены в `build/performance-audit/offline-results.json` и `build/performance-audit/frontend-results.json`, результаты исправленной версии — в `offline-after.json` и `frontend-after.json` той же локальной папки (gitignored).

Приведённые ниже исходные результаты относятся к аудиту до T-367. Скрипты обновлены для проверки исправленной реализации; текущий запуск выдаёт результаты после исправления. Production-данные и настройки не менялись.
