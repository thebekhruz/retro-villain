# Retro Milliy

Модульный веб-дашборд ресторана. Модуль кассира работает с iiko; модуль
финансового отдела пока использует отдельный демонстрационный учёт.
Python 3.11+, FastAPI, мобильный HTML/CSS/JS интерфейс.

Модуль директора доступен по `/director`. Он собирает последние десять
завершённых дней iiko, разделяет Retro/Oxbridge/Yandex и формирует сохранённый
PDF после настройки `GEMINI_API_KEY` и `GEMINI_MODEL` в `build/.env`. До
настройки Gemini кнопка отчёта честно сообщает об ошибке конфигурации. История
отчётов хранится в `director.sqlite3` в едином `RETRO_DATA_DIR`;
его нужно резервировать вместе с базами кассы и бухгалтерии.

Модуль «Учредитель» доступен по `/founder`. Он строит read-only аналитику
выручки и способов оплаты за произвольный диапазон с группировкой по дням,
неделям (с понедельника) или месяцам. Обе границы периода включены, календарь —
`Asia/Tashkent`; быстрые периоды на 7 и 30 дней заканчиваются вчера, а текущий
месяц явно помечает незавершённый сегодняшний день.

Для аналитики выполняются два независимых OLAP-запроса: выручка группируется по
`OpenDate.Typed → CashRegisterName → RestaurantSection`, а оплаты дополнительно
по `PayTypes`. В обоих запросах используются `DishDiscountSumInt` и
`OperationType=PAYMENT`; фильтров по блюдам или группам меню нет. Поэтому новые
предоплаты не становятся выручкой продаж. Подписанные отрицательные суммы внутри
`PAYMENT` сохраняются и уменьшают выручку/оплаты своей даты. На источнике за
2026-08-20…2026-09-18 отдельного типа возврата не найдено: были только «Оплата»,
«Предоплата» и нулевая строка «(без оплаты)». Если iiko начнёт отдавать возврат
отдельным типом операции, он не будет молча смешан с продажами и правило нужно
будет проверить заново.

Классификация отделений закрытая: у `GL-Kassa-Oksbrich` разрешён только `Зал`;
у `Kassa-FiscalBox1` — `2.1 Бар мили`, `Бар Рестаран`, `Вынос`, `Доставка`,
`Летка`, `Напитки Мили`, `Напитки Ресторан`, `Ресторан`, `Ресторан Алкоголь` и
отдельный банкет `Бехруз (Свадьба)`. Этот allowlist снят с live iiko за
2026-08-20…2026-09-18. Любая новая касса или секция блокирует отчёт до ручной
классификации, а не попадает в Retro по умолчанию.

Контрольная live-сверка 2026-09-19:

- 2026-09-15: Retro 31 824 000, школа 3 970 000, оплаченный банкет 0,
  итого продаж и `PayTypes` 35 794 000 сум, расхождение 0. Дополнительные
  22 190 000 банкетного отделения iiko классифицировал как «Предоплата», поэтому
  они корректно не прибавлены к выручке продаж.
- 2026-09-12…2026-09-18: Retro 308 286 500, школа 19 705 500, оплаченный
  банкет 0, итого продаж и оплат 327 992 000 сум, расхождение 0.
- 2026-08-20…2026-09-18: итог продаж и оплат 1 391 151 100 сум,
  расхождение 0; неизвестных касс и способов оплаты не обнаружено.

Минимальная конфигурация Gemini в `build/.env`:

```env
GEMINI_API_KEY=your-key
GEMINI_MODEL=gemini-2.5-flash
```

## Запуск

```sh
python3 -m venv build/venv
build/venv/bin/pip install -r requirements-dev.txt
build/venv/bin/python -m uvicorn retro.app:app --host 127.0.0.1 --port 8010 --no-proxy-headers
```

Открыть http://127.0.0.1:8010. Демонстрация: http://127.0.0.1:8010/?demo=1.
Демонстрация **никогда не включается автоматически** при недоступном iiko.
Она помечается на экране, в имени Excel и внутри файла.

### Постоянная локальная служба (Linux / systemd)

Для работы после закрытия терминала запускать отдельной пользовательской
службой, а не оставлять сервер дочерним процессом временной сессии:

```sh
mkdir -p ~/.config/systemd/user
# создайте ~/.config/systemd/user/retro-villain.service по образцу ниже
systemctl --user daemon-reload
systemctl --user enable --now retro-villain.service
```

Выполнять из корня retro-app, без уже работающего сервера на порту 8010.
Проверка: `systemctl --user status retro-villain` и
`curl --fail http://127.0.0.1:8010/api/config`. Для работы после
выхода пользователя администратор должен один раз включить linger:
`loginctl enable-linger "$USER"`.

Пример unit-файла (подставьте абсолютный путь к checkout):

```ini
[Unit]
Description=Retro Villain dashboard
After=network-online.target

[Service]
Type=simple
WorkingDirectory=/opt/retro-villain
EnvironmentFile=/opt/retro-villain/build/.env
ExecStart=/opt/retro-villain/build/venv/bin/python -m uvicorn retro.app:app --host 127.0.0.1 --port 8010 --no-proxy-headers
Restart=on-failure
RestartSec=3
UMask=0077

[Install]
WantedBy=default.target
```

### Размещение на хостинге

В репозитории лежат `Procfile` и `railway.json`: сервер поднимается командой
`uvicorn retro.app:app --host 0.0.0.0 --port $PORT --no-proxy-headers`.
Заголовки прокси uvicorn не разбирает намеренно — реальный адрес клиента
приложение берёт само и только из сети, указанной в `TRUSTED_PROXY_NETWORK`.

Рабочие SQLite лежат вне checkout, по умолчанию в `~/.local/share/retro-villain`.
На хостинге файловая система пересоздаётся при каждом выкате, поэтому
подключите диск и укажите его каталог:

```env
RETRO_DATA_DIR=/data
```

Что задать в переменных хостинга:

| Переменная | Зачем |
|---|---|
| `DASHBOARD_PANEL_USERS` | вход по ролям: кассир, бухгалтер, директор, учредитель и необязательный администратор |
| `DASHBOARD_USER`, `DASHBOARD_PASSWORD` | общий вход, если роли не нужны |
| `RETRO_DATA_DIR` | каталог на подключённом диске |
| `TRUSTED_PROXY_NETWORK` | подсеть обратного прокси хостинга |
| `IIKO_LOGIN`, `IIKO_PASSWORD` | доступ к выгрузкам |
| `IIKO_DIRECTOR_CATEGORIES` | группы блюд для отчёта директора |
| `GEMINI_API_KEY` | разбор отчёта директора |

Панель закрыта по умолчанию: пока не задан ни один пароль, всё, что пришло
не с петли, получает 403. Пароли задавайте только в переменных окружения
хостинга, в репозиторий они не попадают.

**Модуль финансового отдела на хостинге останется закрытым.** Он пускает
только с той же машины, где работает сервер, и снаружи отвечает 403 — даже
учётной записи бухгалтера. Это сделано осознанно: зарплаты и остатки кассы
не выходят за пределы локальной машины. Кассир, директор и учредитель
работают удалённо без ограничений.

### Просмотр из локальной сети

Для доступа по локальной сети можно настроить `DASHBOARD_USER`,
`DASHBOARD_PASSWORD` и `DASHBOARD_ALLOWED_NETWORK` в защищённом `build/.env`.
Для доступа коллег из той же сети приложение можно запустить на `0.0.0.0:8010`
вместо `127.0.0.1:8010`; тогда адресом будет локальный IPv4 компьютера.
Ограничение подсети и пароль проверяются приложением для каждого запроса.
Это HTTP в локальной сети; для доступа через интернет нужен HTTPS.
Перед привязкой к `0.0.0.0` обязательно проверьте пароль, CIDR и firewall.

### Внешняя публикация

Не публикуйте этот MVP через временный туннель. HTTP Basic Auth
защищает общий dashboard, но финансовые маршруты намеренно доступны
только с loopback Host и loopback-адреса. Для внешнего доступа нужны HTTPS,
полноценная аутентификация и роли; это вне текущего MVP.

## Подключение iiko

Скопировать поля из `config.env.example` в `build/.env`, заполнить:

- `IIKO_SERVER_URL=https://retro3158.iikoweb.ru`
- `IIKO_LOGIN`, `IIKO_PASSWORD`
- `IIKO_STORE_ID` — числовой ID филиала iikoWeb, не UUID iiko Cloud.

`build/` уже исключён существующим `.gitignore`. Не хранить секреты в корневом
`.env`: исходный `.gitignore` этого репозитория такие файлы не исключает.
Не передавать секреты в URL, frontend, файлах отчётов, логах или коммитах.
После настройки перезапустить сервер. Готовность подключения означает только
наличие настроек, не успешную live-проверку.

## Подключение Telegram API бронирований

Для блока бронирований в модуле «Учредитель» добавить в `build/.env` обе
переменные:

- `BOOKING_ANALYTICS_URL` — корневой HTTPS URL сервиса без пути;
- `ANALYTICS_API_TOKEN` — Bearer-токен аналитического API.

Токен используется только сервером и не попадает в браузер. Dashboard запрашивает
агрегаты по дате визита: отправленные заявки, гостей, брони без указанного числа
гостей, отмены и источники. Персональные данные и список отдельных броней не
загружаются. Если Telegram API недоступен, блок показывает локальную ошибку, а
аналитика iiko продолжает работать.

Адаптер использует протокол рабочего Apps Script: `/api/auth/login`,
`/api/olap/init`, `/api/olap/fetch/{id}/grouped-table`. Это iikoWeb, не iiko Cloud.
Исходный Apps Script прочитан из проекта «Retro Milliy — iiko отчёт» 16.09.2026.
Авторизация, обязательный `Accept: application/json`, фильтры удалённых строк
и ограниченный опрос готовности перенесены в Python. Сам Apps Script не менялся.

## Значения

- День: `OpenDate.Typed`, как в существующем Apps Script. Сегодня вычисляется
  в `Asia/Tashkent`. Это день iiko по этому полю, не произвольный 24-часовой срез.
- Продажи после скидок: `DishDiscountSumInt`. Из всего филиала отдельно
  определяются три направления: Retro (`Kassa-FiscalBox1`, кроме отделения
  `Бехруз (Свадьба)`), школа (`GL-Kassa-Oksbrich`) и банкетный зал Бехруз
  (`Kassa-FiscalBox1` + `Бехруз (Свадьба)`). Новый кассовый аппарат не
  причисляется к Retro молча: отчёт останавливается до проверки.
- На экране и в XLSX кассира — только продажи Retro с типом операции
  `PAYMENT`. Полное разделение филиала есть в ответе API (`revenue_breakdown`),
  но школа и банкет в Excel не попадают. Новые предоплаты учитываются отдельно
  через суммы кассовой смены; зачёт старых предоплат нельзя повторно считать
  новым поступлением текущего дня.
- Чеков: `UniqOrderId.OrdersCount`, отдельный агрегат по дню.
  Не суммируется по блюдам или типам оплаты.
- Средний чек: продажи / количество чеков; при нуле чеков отсутствует.
- Способы: `PayTypes`, отдельные типы с распределением суммы самим iiko.
  `PayTypes.Combo` больше не используется. Источники из iiko:
  Демо, UzCard, Наличные (Инкасса QR), Xumo, Я Rahmat, Яндекс Еда,
  Click/Payme Безналичный перевод и Uzum (он встречается в исторических днях).
  Демо не переименовывается в наличные.
  Только известная опечатка iiko «Яндех Еда» отображается как «Яндекс Еда».
  Отсутствующий в успешной полной выборке источник показывается с нулём.
  Нулевая служебная строка «(без оплаты)» исключается. Неизвестный источник
  блокирует отчёт: его сумма не теряется и не распределяется догадкой.
- Удалённые заказы и позиции, void и non-business payments исключены как в
  рабочем Apps Script. Разделение строится по всему филиалу без фильтра по блюдам;
  для отчёта кассира применяется указанный выше фильтр Retro.
- Сумма по оплатам сверяется с дневным итогом, допустимая разница 1 сум.
  Ошибки/неполные данные не заменяются нулями. Пустой день — обе выборки пусты.

## Excel

Шаблон: `retro/modules/cashier/templates/cashier.xlsx`, макет
пользовательского «Любовь Отчёт.xlsx» без старых операций и личных данных.
Подготовлен `scripts/prepare_template.py`. Исходный файл пользователя не изменён.
Шаблон не перезаписывается при скачивании.
Лист «отчет» сохраняет макет, удаляет старые операции, заполняет дату, продажи,
количество чеков, средний чек. Лист «Касса» — полный список оплат с итогом.
Ручные расходы, прочие поступления, новые предоплаты и расчётная сумма к
передаче выводятся на первом листе и на отдельном листе «Расходы». Новые
предоплаты разделены на общую и наличную сумму по кассовой смене iiko, но не
расписаны по всем безналичным способам. Расчёт не подтверждает фактическую
передачу денег без сверки кассира.

Все восемь известных источников автоматически заполняются на первом листе в C3:D10,
итог в D11. На «Касса» дополнительно указана доля выручки. Ручные соответствия
`IIKO_PAYMENT_CELLS` больше не используются. Предыдущие скачанные файлы
не изменяются — после обновления приложения скачать отчёт заново.

Экспорт использует снимок, показанный на странице (хранится до 15 минут,
до 64 снимков, только в памяти). Истёкший снимок требует обновления, а не
скачивает незаметно изменившиеся суммы. Один процесс/worker для этого MVP.
После рестарта все снимки теряются; исходные данные остаются в iiko.

## Ручные операции, предоплаты и сумма к передаче

Кассир выбирает день, вносит каждый расход наличными или прочее поступление
наличными отдельной строкой (название и сумма), при ошибке удаляет строку и
добавляет правильную. Данные сохраняются
в `cashier.sqlite3` в едином `RETRO_DATA_DIR` и не исчезают при перезапуске.
Для сохранности нужны ежедневные проверяемые резервные копии.
В демонстрационном режиме ручной ввод отключён и реальные операции в демо-XLSX
не попадают.

Новые предоплаты всеми способами = `payOrders` кассовой смены − продажи Retro.
Новые предоплаты наличными = `salesCash` − («Демо» + «Наличные (Инкасса QR)»
из оплаченных продаж). Общий приход = продажи + все новые предоплаты + прочие
поступления наличными. «К передаче в финансовый отдел» = «Демо» + новые
предоплаты наличными + прочие поступления наличными − расходы наличными.
Безналичные предоплаты в сумму наличных к передаче не входят. Отрицательный
результат отображается, а не превращается в ноль. Это расчётное значение,
не отметка о фактической передаче. За 15.09.2026: 14 839 000 + 600 000 −
2 003 000 = 13 436 000 сум. За 25.04.2026 расхождение с ручным отчётом
ещё не расследовано; этот день не считать подтверждённым.

Ручную запись расходов и весь финансовый модуль разрешено тестировать только
локально. Публичная ссылка не обходит это ограничение.

## Модуль финансового отдела — локальная демонстрация

Открыть `/accountant`. Перед первым просмотром импортировать лист **«ЗП»**
из полученной от владельца книги. Только этот лист содержит реестр сотрудников;
исходный XLSX остаётся вне репозитория. Пример:

```sh
build/venv/bin/python scripts/import_accountant_roster.py "/путь/к/зп.xlsx"
```

Для полной замены текущего реестра данными из нового листа используйте флаг
`--replace`. Импорт берёт лист «ЗП», колонки «ФИО», «Должность» и сумму,
пропускает пустые строки и строки итогов:

```sh
PYTHONPATH=. build/venv/bin/python scripts/import_accountant_roster.py "/путь/к/зп.xlsx" --replace
```

Импорт сохраняет сотрудников в `accountant.sqlite3` в `RETRO_DATA_DIR`; ставки,
отсутствующие в исходнике, не угадываются и отмечаются как «Нет ставки».
Исправление ставки через API требует причины и записывается в историю изменений.
База финансового отдела отдельная от `cashier.sqlite3` и требует
собственной резервной копии. Данные из неё **не меняют** кассовый отчёт.

По умолчанию показывается вчерашний день. На основной странице список
**опоздавших** раскрывается и сворачивается; отдельная страница
`/accountant/employees` показывает весь реестр по группам. Оба экрана
сохраняют выбранную дату при переходе. С основного экрана можно скачать XLSX
только с опоздавшими, с отдельной страницы — со всеми сотрудниками.
Оба файла явно помечены **ДЕМО**. Проходы Hikvision детерминированно
смоделированы для наглядного теста; реальный ресторанный Hikvision не
подключён, реальные ID сотрудников не назначены. После 10:00 показывается
опоздание, но ставка не уменьшается. Отсутствующий вход даёт нулевое
начисление; сотрудник без демопривязки блокируется до подключения, кроме
одного подтверждённого руководителем дня. Пустые ставки не начисляются.
Нельзя считать эти демонстрационные сведения фактической посещаемостью.

Подтверждённая зарплата создаёт обязательство и не списывает деньги до
фактической выплаты. В основном журнале теперь можно указать общую сумму
расхода и сколько выплачено сразу. Неоплаченная часть попадает в список
долгов; последующая выплата уменьшает долг и денежный остаток в день оплаты.
При пустом поле «Оплачено сейчас» считается, что расход оплачен полностью.
Сумма «К передаче» за выбранный день
автоматически берётся из отчёта кассира (iiko + кассовые предоплаты и ручные
кассовые операции). Финансовый отдел вручную фиксирует расходы по категориям
и деньги Шоху на закуп. Начальный остаток наличных бухгалтера задаётся один
раз на первый день учёта; подтверждение передачи кассиром отдельно не вводится.
Старые записи сохранены в базе. Справочник категорий взят из листа «Категории» книги
«РЕТРО_Лина апрель 2026.xls»: зарплата, административные, операционные,
маркетинг, коммунальные/охрана, закуп и дивиденды/переводы. Доходы и скидки
не предлагаются как расходы. При добавлении расхода выбираются категория,
тип и наименование. Старые записи с произвольным текстом сохраняются;
база мигрирует без их удаления. Оплаченная часть зарплаты показывается
в выплатах за день; неоплаченная часть остаётся долгом.

Остаток на конец выбранного дня = подтверждённый остаток на начало дня +
«К передаче» у кассира за этот день − фактические выплаты − суммы, отложенные
в резерв. Первый день начинается с явно указанного начального остатка либо с
нуля, о чём интерфейс предупреждает. Для переноса между днями нужны кассовые
отчёты за каждый промежуточный день; при пропуске остаток помечается как
нерассчитанный, расходы с выплатой блокируются до загрузки пропущенного дня.
Если iiko недоступен, несуществующее поступление не подменяется нулём.
Неоплаченный расход влияет на долг, а не на остаток денег.

При нехватке денег экран показывает недостачу и стоимость смен по группам.
Пауза группы — только сценарий для решения финансового отдела: приложение
никого не закрывает автоматически и не отменяет уже начисленную зарплату.
Расход «Зарплата» не создаётся на лету. Историческую политику можно установить
только явной идемпотентной командой `scripts/retro_data.py seed-cashier-expense`.
Перед фактической выплатой нужно проверить, не была ли она уже выдана. Старый адрес выгрузки проходов
`/api/accountant/entrances/export` остаётся пустым до реального подключения
Hikvision; новые выгрузки сотрудников содержат только демонстрационные
данные и не заменяют фактический журнал входов.

Персональные данные и изменения финансового отдела пока доступны только
с самой машины: решает адрес соединения (`127.0.0.1` / `::1`), заголовок
HTTP Host остаётся дополнительным ограничителем. Раньше проверялся только
Host, и запрос из сети ресторана с `Host: localhost` открывал модуль по
общему паролю дашборда. Публиковать этот модуль через Cloudflare Tunnel или
давать сетевой доступ нельзя без полноценной авторизации и разграничения
ролей: за туннелем все запросы приходят с localhost, и проверка адреса их
не отличает. Отдельных ролей (кассир, бухгалтер, директор) в приложении нет —
пароль дашборда один на всех.

## Доступ с телефона и публикация

По умолчанию сервер слушает **только 127.0.0.1**. Для просмотра с телефона
нужны размещение в доверенной сети, HTTPS и настроенная аутентификация.
Если указать `DASHBOARD_USER` и `DASHBOARD_PASSWORD`, включится HTTP Basic Auth.
`DASHBOARD_ALLOWED_NETWORK` дополнительно ограничивает клиентов указанной
подсетью (например, `10.10.8.0/22`); localhost остаётся доступен после входа.
Без `DASHBOARD_PASSWORD` все нелокальные запросы отвергаются. Даже при заданном пароле
финансовые URL остаются loopback-only.
За постоянным reverse proxy защита должна быть обязательно настроена: адрес proxy не
подтверждает личность пользователя. Не включать доверие произвольным
X-Forwarded-For. Использовать HTTPS, закрыть прямой доступ к upstream.
Персональные роли, история действий и хранилище пользователей пока вне MVP.
Постоянный защищённый публичный деплой не выполнен.

## Хранилище и резервные копии

Рабочие базы кассы, бухгалтерии и директора находятся в едином каталоге,
заданном `RETRO_DATA_DIR`. Если переменная пуста, используется
`~/.local/share/retro-villain`. Каталог создаётся с правами `0700`, базы —
с правами `0600`; разные git worktree поэтому читают одну историю.

Проверка существующей базы не выводит строки или персональные данные:

```sh
PYTHONPATH=. build/venv/bin/python scripts/retro_data.py verify \
  --source /путь/к/cashier.sqlite3
```

Для первого переноса команда `migrate` сначала делает online-backup SQLite,
проверяет hash и `PRAGMA integrity_check`, затем устанавливает только
проверенные копии. Исходные файлы не удаляются. Непустой каталог назначения
не перезаписывается без явного `--replace`:

```sh
PYTHONPATH=. build/venv/bin/python scripts/retro_data.py migrate \
  --cashier /старый/build/cashier.sqlite3 \
  --accountant /старый/build/accountant-demo.sqlite3 \
  --backup-root /защищённый/каталог/backups \
  --destination "$RETRO_DATA_DIR"
```

`restore` требует отдельный каталог назначения и сначала повторно проверяет
manifest, SHA-256 и целостность каждой базы. Перед реальным переключением
сервиса восстановление нужно репетировать во временный каталог.

Ежедневно запускайте `retro_data.py backup` в каталог на другом носителе и
проверяйте код завершения. Не реже раза в месяц выполняйте `restore` в
новый временный каталог, затем `verify` для всех трёх баз. Никогда не восстанавливайте
поверх рабочего каталога без остановки сервиса и отдельной свежей копии.

Проверка прав не читает содержимое файлов:

```sh
python3 scripts/check_runtime_permissions.py build/.env "$RETRO_DATA_DIR" \
  "$RETRO_DATA_DIR"/*.sqlite3
```

## Переменные окружения

- `IIKO_SERVER_URL`, `IIKO_LOGIN`, `IIKO_PASSWORD`, `IIKO_STORE_ID` — доступ к iiko.
- `ACCOUNTANT_MANUAL_HANDOVER` — `1` для явных передач кассы, `0` для iiko fallback.
- `RETRO_DATA_DIR` — общий каталог `cashier.sqlite3`, `accountant.sqlite3`, `director.sqlite3`.
- `GEMINI_API_KEY`, `GEMINI_MODEL` — серверный AI-анализ отчёта директора.
- `DIRECTOR_REPORT_RETENTION` — число хранимых отчётов.
- `IIKO_DIRECTOR_CATEGORIES`, `IIKO_DIRECTOR_EXCLUDED_GROUPS` — явная классификация меню.
- `DASHBOARD_USER`, `DASHBOARD_PASSWORD` — Basic Auth для всего dashboard.
- `DASHBOARD_PANEL_USERS` — ролевые записи в формате `user:password:role;...`.
  Обязательные роли: `cashier`, `accountant`, `director`, `founder`; необязательная
  роль `admin` получает доступ ко всем страницам и API. Для каждой указанной роли
  задайте ровно один уникальный логин.
- `DASHBOARD_ALLOWED_NETWORK` — необязательная CIDR-подсеть клиентов.
- `TRUSTED_PROXY_NETWORK` — только CIDR самого reverse proxy. За его пределами
  `X-Forwarded-For` игнорируется; не указывайте там клиентскую подсеть.
- `BOOKING_ANALYTICS_URL`, `ANALYTICS_API_TOKEN` — агрегированная аналитика бронирований.

`build/.env` должен иметь права `0600`. Секреты не передаются в URL,
логи, frontend или Git. Полный образец находится в `config.env.example`.

## Проверки

```sh
build/venv/bin/python -m pytest -q
```

Проверяются расчёты, несовпадение сумм, даты, пустой день, невалидные ответы,
исходные значения шаблона, Excel formula injection, защита API, выбор снимка
и протокол iiko (на HTTP-фикстурах). Для живой проверки нужны настройки выше.
16.09.2026 выполнена live-проверка за 15.09: весь филиал 58 284 000 сум,
из них Retro 32 124 000, школа 3 970 000, зал Бехруз 22 190 000.
Кассовые продажи Retro (`PAYMENT`) — 31 824 000 сум, 75 чеков;
сумма по оплатам совпала. «Демо» в названиях некоторых типов оплат —
исходное имя iiko, не режим демонстрации приложения.
